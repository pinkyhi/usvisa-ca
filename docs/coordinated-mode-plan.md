# План coordinated режима для Node и Coordinator

Реализация доступна в репозитории: Node, Coordinator, портал, RabbitMQ и три профиля публикации. Пошаговый запуск, смена профиля, резервное копирование и тесты описаны в [инструкции запуска](coordinated-setup.md). Ниже сохранены архитектура и контракт.

Последняя проверка: 174 unit теста проходят. В реальном Docker проверены Chromium, автовход Node в портал, выдача токена, получение расписания, повторный запуск с тем же nodeId, обнаружение нового Quick Tunnel hostname и первая проверка дат с HTTP 200. Ранее также выполнены 3 opt-in интеграционные проверки брокера и внешнего HTTPS/WSS с подменённой визовой сессией; в этих проверках booking POST и SMTP не выполнялись.

Обычный `docker compose up -d --build` запускает Node и выбранную инфраструктуру. `MODE=solo` включает только Node; `MODE=coordinated` добавляет Coordinator, RabbitMQ, edge и connector выбранного `EXPOSE_MODE`. `COMPOSE_PROFILES` вычисляется из этих двух настроек в `.env`. Для локальной ноды достаточно сохранённых `PORTAL_USERNAME`/`PORTAL_PASSWORD`: регистрация использует постоянный idempotency key, токен сохраняется в `.node-state/registration.json`, после heartbeat приходит расписание и начинает работать прежний worker. Node хранит отдельные данные визового аккаунта; Coordinator их не получает. `server.py up --mode ...` также останавливает сервисы, не нужные новому режиму.

Добавляем совместную проверку доступности для одной группы одного консульства. Каждая нода сохраняет собственный аккаунт, ограничения дат и бронирование. Coordinator распределяет время обычных проверок и адресно передаёт полезные находки.

Первый шаг реализации — разложить существующий код по пакетам с сохранением solo режима. Затем добавить RabbitMQ, Coordinator и портал автоматической выдачи доступа.

## Принятые решения

| Область | Решение |
| --- | --- |
| Режимы | MODE=solo или MODE=coordinated при запуске |
| Группа | Одна группа с общими consulateId и city |
| Обычные проверки | Каждая нода раз в 180 секунд с равномерным сдвигом фаз |
| Подключение | Три профиля: tailscale, cloudflare_quick, cloudflare_domain |
| Транспорт ноды | Общий Web STOMP 1.2 через WSS во всех профилях |
| Транспорт Coordinator | AMQP 0-9-1 по внутренней сети сервера |
| Сервер | Домашний сервер с одним RabbitMQ и одним процессом Coordinator |
| Хранение | SQLite Coordinator и постоянный том RabbitMQ |
| Доступ ноды | Индивидуальный токен; RabbitMQ пользователь и очередь создаются порталом |
| Heartbeat | nodeId, личный minDate, последний scheduleVersion |
| Отсутствие | Через 540 секунд без свежего heartbeat нода исключается из активного расписания |
| Расписание | Полный персональный снимок; scheduleVersion как UUID и revision как число |
| Срок расписания | Без validUntil; последнее назначение действует до замены |
| Общий порог находок | reportBefore = max(minDate активных нод) |
| Получатели находки | Другие активные ноды, для которых date < личного minDate |
| Маршрутизация | Три direct exchange, без fanout |
| Срок находки | 180 секунд от observedAt, включая все этапы доставки |

Две ноды проверяют со сдвигом 90 секунд, три — 60 секунд. Это уменьшает промежуток между наблюдениями группы, сохраняя обычную частоту каждого аккаунта. Паузы и разрывы связи могут временно создавать пропуски или совпадения фаз.

## Сохранение текущего поведения

Solo сохраняет существующие настройки и поведение:

- Вход через Selenium, последующие запросы через requests и переиспользование сессий.
- Личный диапазон дат, исключения и число заявителей.
- TEST_MODE, обычные задержки и паузы между циклами.
- HTTP 429, Retry-After, backoff и переавторизацию.
- Проверку результата бронирования и остановку при неопределённом результате.
- Gmail уведомления, журналы доступности и аудит.
- Постоянную защиту от второго booking POST для той же заявки.

MODE по умолчанию — solo. Переключение выполняется изменением настройки и перезапуском процесса. Solo не требует новых сервисов.

В coordinated сервер задаёт обычный период 180 секунд. Локальные cooldown, backoff, пауза цикла и незавершённая работа могут отложить проверку. Heartbeat продолжает работать отдельно во время входа, бронирования и пауз; рабочего статуса в нём нет.

## Сеть и сервер

Владелец сервера выбирает EXPOSE_MODE=tailscale, cloudflare_quick или cloudflare_domain. Это независимая настройка от MODE=solo/coordinated у ноды. При запуске используется один профиль публикации; переход выполняется сменой конфигурации и перезапуском инфраструктуры.

### Общий транспорт трёх профилей

Node использует одинаковый Web STOMP 1.2 поверх WSS. Меняются адрес и способ публикации сервера, без трёх реализаций клиентского протокола. Coordinator работает с тем же RabbitMQ через внутренний AMQP.

Один HTTPS origin обслуживает портал и WebSocket endpoint /ws. Локальный Nginx направляет /ws в RabbitMQ Web STOMP, остальные пути — в Coordinator. Он передаёт STOMP кадры прозрачно, без собственных подтверждений сообщений и без административного доступа к брокеру. [RabbitMQ Web STOMP](https://www.rabbitmq.com/docs/web-stomp)

~~~mermaid
flowchart LR
    N["Node"]
    U["Браузер"]
    E["Tailscale Serve или Cloudflare Tunnel"]
    subgraph Home["Домашний сервер"]
        P["Nginx HTTP маршрутизатор"]
        R["RabbitMQ и Web STOMP"]
        C["Coordinator и портал"]
        DB[("SQLite")]
        P <-->|"/ws"| R
        P -->|"Остальные пути"| C
        R <-->|"AMQP внутри Compose"| C

    end

    U <-->|"HTTPS"| E
    E <--> P
    N -->|"Свой интернет и аккаунт"| V["Визовый сайт"]
~~~

Docker Compose запускает RabbitMQ, Coordinator и Nginx. Для Cloudflare профилей добавляется cloudflared; Tailscale и Serve в приватном профиле работают на хосте.

| Порт | Доступ |
| --- | --- |
| HTTPS/WSS 443 | Единственная внешняя точка входа выбранного профиля |
| HTTP 8080 | Nginx, на хосте только 127.0.0.1 для Serve или локального cloudflared |
| AMQP 5672 | Только внутри сети Compose, используется Coordinator |
| Web STOMP 15674 | Только внутри сети Compose, используется Nginx |
| Management API 15672 | Только внутри сети Compose; диагностическая публикация на хост допускается только на localhost |
| Backend Coordinator | Только внутри сети Compose, за Nginx |

Белый или статический IP и входящие порты роутера не требуются ни в одном варианте. Визовый сайт нода посещает через свой интернет; трафик аккаунта не направляется через сервер или VPN exit node.

Нода проверяет цепочку TLS сертификата и hostname во всех профилях. Отключение проверки сертификатов не является способом подключения к временным адресам. Reconnect с задержкой и jitter, восстановление подписки, STOMP heartbeat и WebSocket keepalive работают независимо от профиля.

### Профиль Tailscale

EXPOSE_MODE=tailscale. На сервере и компьютерах нод установлен Tailscale. Serve предоставляет HTTPS/WSS адрес вида https://visa-server.tailnet-name.ts.net и проксирует локальный Nginx.

Доступ по tailnet разрешается только выбранным устройствам и пользователям к 443 сервера. AMQP наружу не публикуется. Собственный домен не нужен. [Сеть Tailscale](https://tailscale.com/docs/concepts/what-is-tailscale), [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve)

### Профиль временного Cloudflare Tunnel

EXPOSE_MODE=cloudflare_quick. Бесплатный Quick Tunnel выдаёт случайный HTTPS адрес вида https://random-name.trycloudflare.com; собственный домен и Cloudflare аккаунт не нужны.

При запуске cloudflared на хосте команда:

~~~sh
cloudflared tunnel --url http://127.0.0.1:8080
~~~

В Compose тот же tunnel направляется на http://edge:8080, где edge — сервис Nginx. Один временный origin обслуживает портал и /ws; два отдельных случайных туннеля не требуются.

Адрес действует только пока работает этот Quick Tunnel. При новом запуске hostname меняется: Coordinator и локальная Docker-нода узнают его через внутренний metrics endpoint cloudflared `/quicktunnel`, без Docker socket и публикации metrics на хост. Удалённые ноды обновляют SERVER_URL явно: старый адрес не может сообщить новый после остановки. Токены, очереди и состояние остаются прежними.

Quick Tunnel рассчитан на тестирование, не имеет гарантии доступности и допускает до 200 одновременных запросов. Встроенный email PIN требует браузера и не поддерживает неинтерактивных клиентов: --allowed-mail не включаем на общем origin с /ws. Портал защищён собственным входом, сообщения — персональным RabbitMQ токеном. [Quick Tunnels и ограничения](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)

### Профиль Cloudflare Tunnel на своём домене

EXPOSE_MODE=cloudflare_domain. Нужны Cloudflare аккаунт и домен, настроенный в Cloudflare. Создаётся постоянный named tunnel и hostname, например https://visa.example.com, направленный на тот же Nginx. На нодах нет Tailscale, WARP или cloudflared.

Cloudflared работает на сервере; tunnel credentials остаются серверным секретом. Перезапуск connector сохраняет hostname, ноды переподключаются по прежнему SERVER_URL. Домен используется для HTTPS портала и WSS /ws. [Настройка постоянного Tunnel](https://developers.cloudflare.com/tunnel/get-started/)

Cloudflare Access может быть дополнительным слоем позднее, но три базовых профиля не требуют Access или отдельного machine-to-machine секрета. Если Access включать на /ws, отдельно потребуется поддержка сервисной авторизации скриптов; интерактивный вход пользователя там не используется.

В обоих Cloudflare профилях HTTPS/WSS заканчивается на Cloudflare: сервис технически имеет доступ к содержимому этого канала, включая токен соединения. Пароли и cookies визового сайта остаются локальными. [Модель TLS Cloudflare](https://developers.cloudflare.com/ssl/concepts/)

### Конфигурация адреса и запуск

| EXPOSE_MODE сервера | SERVER_URL ноды |
| --- | --- |
| tailscale | https://visa-server.tailnet-name.ts.net |
| cloudflare_quick | https://random-name.trycloudflare.com |
| cloudflare_domain | https://visa.example.com |

Node получает SERVER_URL и выводит из него WSS адрес /ws. Публичный origin также задаётся как PUBLIC_BASE_URL сервера для точной проверки Host/Origin и формирования конфигурации. Для Quick Tunnel helper сохраняет текущий адрес в runtime конфиге без секретов и синхронизирует PUBLIC_BASE_URL перед выдачей пользовательского конфига; не разрешаем произвольные *.trycloudflare.com origins.

Один набор SQLite, очередей и токенов используется при смене профиля. Смена публичного origin сбрасывает браузерную сессию, но не меняет владельцев или nodeId.

Порядок готовности: RabbitMQ и общая топология, Coordinator, Nginx, выбранный Serve/Tunnel и актуальный PUBLIC_BASE_URL. На сервере один экземпляр планировщика. Runtime данные и тома сохраняются между сменами профилей.

Один домашний сервер не обеспечивает доступность при отказе машины или диска. При недоступности ноды продолжают сохранённое расписание; находки доставляются после восстановления только до истечения срока.

## Портал и токены

Портал — обычные HTML шаблоны FastAPI/Jinja2 с Tailwind, без отдельного React приложения. Общие CSS переменные темы зафиксировать один раз в styles.css через tweakcn. При реализации проверить скриншоты Playwright по отступам, типографике, цветам и контрасту.

Во всех трёх профилях портал имеет собственный вход по логину и паролю. Пользователей создаёт владелец сервера через локальную команду, публичной саморегистрации нет. Email не требуется; логин нормализуется без учёта регистра, пароль — от 8 до 1024 символов. Пароли хранятся как Argon2id хеши, браузерная сессия — отдельный от NODE_TOKEN случайный идентификатор в Secure/HttpOnly/SameSite cookie; вход имеет ограничение попыток.

Приложение показывает только ноды вошедшего пользователя и не доверяет присланным извне Tailscale или Cloudflare identity заголовкам. Собственный вход обеспечивает работу временного домена без Access и делает смену сетевого профиля независимой от учётных записей. Nginx и backend не публикуются напрямую на внешние интерфейсы.

Для /ws браузерная сессия портала не нужна: RabbitMQ проверяет индивидуальный токен в STOMP CONNECT до доступа к сообщениям. Anonymous/default broker login отключён.

Экран содержит свои ноды, имя, последний heartbeat и действия «Создать ноду», «Перевыпустить токен», «Отозвать доступ». При выдаче показываются токен и готовая конфигурация с копированием.

### Создание ноды

1. Пользователь задаёт имя и нажимает «Создать ноду».
2. Coordinator сохраняет владельца и постоянный nodeId со стадией provisioning.
3. Генерирует случайный секрет не менее 256 бит.
4. Через внутренний Management API создаёт пользователя node_{nodeId}, durable очередь, bindings, ограниченные права и лимит одного broker соединения.
5. После готовности ресурсов возвращает токен {nodeId}.{secret} и параметры подключения.
6. Первый свежий heartbeat включает ноду в активное расписание.

Нода выводит RabbitMQ username из nodeId и использует secret как passcode STOMP CONNECT. Общих административных секретов у клиентов нет; JWT для токена ноды не нужен.

Provisioning восстанавливается после частичного сбоя по стабильным nodeId и именам ресурсов. До завершения выдачи утраченный секрет можно заменить новым. Токен не выдаётся раньше готовности пользователя, очереди и прав.

Секрет показывается один раз, постоянно сохраняются только хеши и метаданные. Ответ имеет Cache-Control: no-store; токен не попадает в аудит, URL и access logs. При потере ответа после завершённой выдачи пользователь выпускает новый токен.

Перевыпуск сохраняет nodeId и очередь, меняет секрет и закрывает старые broker соединения, включая Web STOMP. Отзыв блокирует RabbitMQ доступ, закрывает соединения и сразу исключает ноду из активного состава. Отсутствие heartbeat само по себе не удаляет учётную запись и очередь. Отзыв доступа к брокеру не останавливает локальный скрипт с сохранённым расписанием.

Создание пользователей, очередей, прав и управление соединениями доступны через [RabbitMQ Management API](https://www.rabbitmq.com/docs/management). Его административные credentials находятся только у серверной части.

## Расписание и присутствие

Период P = 180 секунд. Для N активных нод назначить равномерные фазы с шагом P / N. При смене состава сохранять относительный циклический порядок оставшихся нод и по возможности фазу одной из них как якорь, затем распределять остальные.

startAt — якорь периодической сетки; может находиться в прошлом. Проверки выбираются среди точек startAt + k × intervalSeconds, k >= 0. Первой ноде дать ближайшее время старта.

| Ноды | Сдвиги фаз |
| --- | --- |
| 1 | 0 секунд |
| 2 | 0 и 90 секунд |
| 3 | 0, 60 и 120 секунд |

При новом назначении нода отменяет прежний ожидающий таймер и выбирает следующую будущую точку. Точки, нарушающие 180 секунд от последнего обычного запроса доступности или локальную паузу, пропускаются. Догоняющей серии запросов нет.

Для реального таймера допускается до одной секунды задержки ОС внутри фазы. Минимальный локальный интервал 180 секунд всё равно соблюдается; задержка в несколько миллисекунд не должна приводить к пропуску каждой второй проверки. Задержки за пределами окна и длинные паузы пропускают фазу.

Локальные интервалы измеряются монотонным временем, общая сетка задаётся в UTC. Сохраняется время последней обычной проверки, чтобы перезапуск не обходил минимальный интервал.

Heartbeat отправляется при подключении и каждые 30 секунд отдельной задачей. Blocking requests/Selenium исполняются отдельным последовательным worker и не блокируют Web STOMP или heartbeat.

Coordinator сохраняет lastSeenAt. После 540 секунд без свежего heartbeat нода исключается, фазы и общий порог пересчитываются. При возвращении нода включается снова. При старте Coordinator восстанавливает состояние и обрабатывает уже истёкшее присутствие.

Изменение только reportBefore или конфигурации создаёт новую версию снимков, сохраняя фазы, если состав и период прежние. Обычный heartbeat без изменений версию не меняет.

### Разрыв связи

У расписания нет validUntil. При недоступном сервере нода продолжает последнее сохранённое назначение; автоматического перехода в solo нет.

Coordinator может исключить её и назначить фазу другому участнику. Поэтому точный сдвиг всех физически работающих нод во время разделения сети не гарантируется. Распределённые claims на каждую проверку не вводятся.

При восстановлении связи нода немедленно отправляет heartbeat с сохранённым scheduleVersion. При первом запуске без снимка она ждёт расписание, затем продолжает опросы в назначенные точки.

Один nodeId — один запущенный экземпляр Node и одно Web STOMP соединение. При provisioning выставить per-user max-connections=1 и проверить его действие для выбранной версии Web STOMP: второй экземпляр с тем же токеном не должен делить очередь с первым. Очередь остаётся durable, не exclusive и без auto-delete. Локальный lock предотвращает повторный запуск на одном компьютере. [Per-user limits](https://www.rabbitmq.com/docs/user-limits)

## Пороги и адресная рассылка

Личный minDate — порог уведомлений: полезна дата строго раньше него. Это отдельная настройка NODE_MIN_DATE. Она не заменяет EARLIEST_ACCEPTABLE_DATE, LATEST_ACCEPTABLE_DATE и исключения для собственного бронирования.

Coordinator хранит личные пороги и сообщает всем одинаковый предварительный порог:

~~~text
reportBefore = max(minDate всех активных нод)
~~~

Нода рассматривает полный ответ доступности до своих личных фильтров. Отправляет даты date < reportBefore, исключая собственную подтверждённую бронь. Личные исключения отправителя не отбрасывают даты, полезные другим.

В TEST_MODE реальной брони нет, подготовленная дата остаётся в находке. При неопределённом исходе POST сохранить остановку и guard; потенциально забронированную дату не объявлять заведомо свободной.

Для каждого другого активного получателя Coordinator формирует:

~~~text
recipientDates = найденные даты, для которых date < recipient.minDate
~~~

При пустом списке публикации нет. Даты сортируются и не повторяются. Перед рассылкой сервер проверяет актуальные пороги и срок находки.

Пример: у Alice minDate 2027-11-01, у Bob 2027-12-01. reportBefore равен 2027-12-01. Найденная Alice незабронированная дата 2027-11-15 доставляется только Bob.

Все подходящие получатели равноправны. Приоритеты между ними вне первой версии.

## RabbitMQ и доставка

Vhost — visa. Общие ресурсы создаются при подготовке сервера, персональные — при выдаче токена.

| Exchange | Тип | Публикует | Routing key | Очередь |
| --- | --- | --- | --- | --- |
| visa.commands | direct | Node | coordinator | visa.coordinator.inbox |
| visa.control | direct | Coordinator | nodeId | visa.node.{nodeId}.inbox |
| visa.slots | direct | Coordinator | nodeId | visa.node.{nodeId}.inbox |

У ноды одна входящая очередь с двумя привязками. Очереди и exchange durable, персональные очереди без auto-delete. Для одного брокера достаточно durable classic очередей.

Права ноды: публикация только в visa.commands, чтение только своей очереди, без configure и management. Клиент не объявляет активно ресурсы при подключении; восстановление соединения должно работать с этими минимальными правами.

STOMP user-id обязателен и преобразуется в AMQP user_id. RabbitMQ сверяет его с пользователем соединения, Coordinator дополнительно сверяет nodeId. Сообщение без подтверждённого user_id не считается аутентифицированным. Тег impersonator нодам не выдаётся. [Validated User-ID](https://www.rabbitmq.com/docs/validated-user-id)

### Подтверждения

- В AMQP Coordinator включить publisher confirms и mandatory.
- Node публикует STOMP SEND с receipt, а находки — также с persistent:true. Локальный outbox ожидает соответствующий RECEIPT, который для persistent сообщения RabbitMQ отправляет после broker confirm.
- Подписка Node использует ack:client-individual. Auto-ack отключён: ACK отправляется после обработки или сохранения задачи для продолжения после сбоя.
- Расписания и находки persistent; heartbeat может быть transient.
- Дубликаты обрабатываются по messageId, порядок расписаний — по revision.
- Постоянно невалидные сообщения отклоняются без requeue с аудитом причины.

Coordinator проверяет наличие общей очереди и binding visa.commands/coordinator перед готовностью сервиса; ноды не могут менять топологию. STOMP RECEIPT не имеет семантики AMQP mandatory и сам по себе не доказывает наличие подходящего маршрута. Постоянная durable топология и её проверка — условие гарантии приёма команд.

Durable очередь и persistent сообщения сохраняются при обычном перезапуске брокера. Publisher confirm и consumer ACK подтверждают разные этапы; подтверждение публикации не означает выполнение бронирования. [Durability](https://www.rabbitmq.com/docs/queues#durability), [Confirms и ACK](https://www.rabbitmq.com/docs/confirms)

| Сообщения | Срок |
| --- | --- |
| node.heartbeat | 60 секунд от sentAt; без локального outbox |
| schedule.updated | Без TTL, с проверкой revision |
| slots.found и slots.available | 180 секунд от observedAt на весь путь |

Каждая повторная публикация использует оставшийся срок, а не новые 180 секунд. Приложение проверяет абсолютное истечение и после получения: сообщение могло устареть вне очереди. [TTL RabbitMQ](https://www.rabbitmq.com/docs/ttl)

Heartbeat старше 60 секунд отклоняется. Допустимое расхождение часов — пять секунд. lastSeenAt учитывается по времени свежего сообщения, ограниченному текущим временем сервера, а не по позднему времени обработки. Повторный или более старый heartbeat не продлевает присутствие и не откатывает minDate.

### Outbox и восстановление

Coordinator одной транзакцией SQLite сохраняет обработанный messageId, изменения состояния и исходящие события в outbox, затем отправляет consumer ACK. Отправитель outbox публикует и ждёт publisher confirm, после чего отмечает запись доставленной брокеру.

Сбой после публикации до отметки вызывает повтор с прежним messageId. Просроченные находки и ожидающие рассылки отозванным адресатам отменяются.

Нода сохраняет исходящие находки до подтверждения брокером или истечения срока. Входящие находки сохраняются как локальные задачи перед ACK; booking выполняется общим последовательным worker, не consumer обработчиком. Guard обязателен при любом источнике кандидата.

## Контракт сообщений

JSON UTF-8, имена полей camelCase. Максимальный размер сообщения — 64 KiB. Неизвестные и повторяющиеся JSON поля отклоняются. UUID передаются в каноническом виде с дефисами и строчными буквами. Даты — YYYY-MM-DD, моменты времени — ISO 8601 в UTC с Z, с точностью до микросекунд. Списки дат нормализуются в уникальные даты по возрастанию.

| Поле конверта | Тип | Правило |
| --- | --- | --- |
| version | integer | 1 |
| type | string | Один из пяти типов ниже |
| messageId | UUID string | Сохраняется при повторной отправке |
| sentAt | UTC datetime string | Время создания |
| data | object | Данные конкретного сообщения |
| inReplyTo | UUID string или отсутствует | Для адресного ответа на исходную команду |

Внутри AMQP content_type = application/json, message_id = messageId, type совпадает с конвертом, user_id равен username publisher. JSON одинаков для всех трёх сетевых профилей.

### Отображение в Web STOMP

- WSS endpoint — /ws того же SERVER_URL, что используется порталом.
- CONNECT: STOMP 1.2, host=visa, login=node_{nodeId}, passcode=secret.
- SEND: destination=/exchange/visa.commands/coordinator.
- SUBSCRIBE: destination=/amq/queue/visa.node.{nodeId}.inbox, ack=client-individual. Используется существующая durable очередь; подписка на /exchange создала бы другую очередь и здесь не подходит.
- Заголовки content-type, type и user-id соответствуют AMQP свойствам. Для идентификатора JSON сообщения использовать amqp-message-id: STOMP message-id и ACK delivery id имеют транспортное назначение.
- У находок persistent:true и expiration с оставшимся TTL в миллисекундах; receipt и receipt-id связывают отправку с подтверждением.
- После разрыва заново CONNECT и SUBSCRIBE, затем свежий прикладной heartbeat и повтор неподтверждённых находок с прежними messageId.

STOMP heartbeat и WebSocket keepalive поддерживают соединение; прикладной node.heartbeat отвечает за присутствие и сверку расписания. [STOMP destinations и свойства](https://www.rabbitmq.com/docs/stomp)

### node.heartbeat

Node → Coordinator через visa.commands.

| Поле data | Тип | Значение |
| --- | --- | --- |
| nodeId | UUID string | Идентификатор из токена |
| minDate | date string | Личный порог уведомлений |
| scheduleVersion | UUID string или null | Последний принятый снимок или отсутствие снимка |

Первый свежий heartbeat готовой ноды включает её в состав. При изменении общего состояния Coordinator рассылает новые персональные снимки всем активным нодам. При неизменном состоянии и несовпадении UUID отвечает снимком только отправителю с inReplyTo. При совпадении отдельного прикладного ответа нет.

### schedule.updated

Coordinator → Node через visa.control.

| Поле data | Тип | Значение |
| --- | --- | --- |
| nodeId | UUID string | Получатель |
| scheduleVersion | UUID string | Общий UUID текущего состояния |
| revision | positive integer | Порядковый номер состояния |
| startAt | UTC datetime string | Якорь персональной сетки |
| intervalSeconds | integer | 180 |
| reportBefore | date string | Максимальный minDate активной группы |
| config | object | Общие consulateId как integer и city как string |

У всех персональных снимков одного состояния одинаковые UUID и revision. UUID нужен для равенства версий, revision — для порядка. Они сохраняются в SQLite и не сбрасываются при обычном рестарте.

Нода сохраняет снимок атомарно перед ACK. Меньшую revision игнорирует и подтверждает; равную с тем же UUID не применяет повторно и не перезапускает таймер. Равная revision с другим UUID — нарушение протокола. Большая revision заменяет весь снимок.

Данных остальных нод в снимке нет. ConsulateId и city сверяются с локальным клиентом; несовпадение требует исправления конфигурации без молчаливого выбора другого города.

### slots.found

Node → Coordinator через visa.commands.

| Поле data | Тип | Значение |
| --- | --- | --- |
| nodeId | UUID string | Источник |
| observedAt | UTC datetime string | Время получения ответа о доступности |
| dates | array of date strings | Непустой список раньше reportBefore без собственной подтверждённой брони |

Срок — observedAt + 180 секунд. Повторы сохраняют messageId и observedAt. Coordinator проверяет источник, возраст, уникальность и даты, затем создаёт персональные рассылки.

После собственного подтверждённого booking сохранить в SQLite флаг `verified_booking`, отключающий дальнейшее бронирование, и остальные полезные даты в outbox. Продолжить обычные проверки, heartbeat и отправку находок без собственной забронированной даты. Перед остановкой пользователем ограниченно дождаться публикации outbox. Ошибка Gmail или брокера не должна терять локально сохранённый пакет или разрешать повторную бронь.

### slots.available

Coordinator → конкретная Node через visa.slots.

| Поле data | Тип | Значение |
| --- | --- | --- |
| findingId | UUID string | messageId исходного slots.found |
| sourceNodeId | UUID string | Источник наблюдения |
| observedAt | UTC datetime string | Исходное время |
| expiresAt | UTC datetime string | observedAt + 180 секунд |
| dates | array of date strings | Даты, прошедшие личный minDate получателя |

Конверт имеет собственный messageId, сохраняемый при повторе этой адресной публикации. findingId связывает рассылки с одной находкой.

Получатель проверяет срок, дубликаты, свой диапазон и исключения и передаёт кандидатов общему worker. Событие не требует внеочередного запроса полного списка дат: время и форма проверяются существующим booking кодом. Backoff, TEST_MODE и guard сохраняются.

После подтверждённого успеха выводится зелёное сообщение капсом; coordinated-нода переходит к дальнейшему мониторингу без booking, включая полученные от других нод слоты. Состояние сохраняется после перезапуска. Неопределённый исход сохраняет остановку для ручной проверки. Повтор события не разрешает второй booking POST.

### error

Coordinator → отправитель через visa.control. В data — code и message, inReplyTo ссылается на отклонённую команду, если отправитель и идентификатор установлены.

Коды: INVALID_MESSAGE, UNSUPPORTED_VERSION, NODE_ID_MISMATCH, NODE_REVOKED, INVALID_MIN_DATE, INVALID_SCHEDULE_VERSION, INVALID_OBSERVED_AT. Секретов и тел ответов визового сайта в ошибках нет.

Отдельных state.get, check.claim, dueAt, check.completed, booking.report, slots.accepted, events.ack и node.leave нет. Транспортные ACK не являются JSON сообщениями.

## HTTP контракт портала

HTTP API используется браузером во всех профилях. После выдачи токена рабочий протокол ноды — Web STOMP поверх WSS.

| Метод и путь | Вход | Результат |
| --- | --- | --- |
| POST /api/v1/session | username и password | Вход, 200 и защищённая session cookie |
| DELETE /api/v1/session | Session | Выход, 204 и отзыв сессии |
| GET /api/v1/me | Session | Личность пользователя |
| GET /api/v1/nodes | Session | Свои ноды и метаданные без секретов |
| POST /api/v1/nodes | name, Idempotency-Key | Создание ресурсов; 201 с nodeId, token и connection |
| POST /api/v1/nodes/{nodeId}/token | Idempotency-Key | Перевыпуск; 200 с token и connection |
| POST /api/v1/nodes/{nodeId}/revoke | Session владельца | Отзыв; 204 |

Connection содержит serverUrl, websocketUrl, vhost и inboxQueue. Username выводится из nodeId. Конфиг ноды не содержит административных credentials и не требует отдельного пароля RabbitMQ.

Изменяющие запросы проверяют точный Origin и CSRF. Сессии имеют срок и отзываются при выходе или блокировке пользователя. Ошибки: 401 без сессии/при неверном входе, 403 для заблокированного пользователя, 404 для чужой/отсутствующей ноды, 422 для невалидного входа, 429 при превышении попыток входа и 503 при недоступном provisioning.

Idempotency-Key предотвращает второго пользователя RabbitMQ или повторную ротацию при повторе одного запроса. Секрет завершённой выдачи повторно не возвращается: повтор выдаёт метаданные той же ноды и необходимость перевыпуска при потере секрета. Состояние операции позволяет дозавершить частичное создание ресурсов.

Локальное состояние Node: снимок расписания, последняя обычная проверка, входящие задачи, исходящие находки и флаг подтверждённой брони `verified_booking`. Cookies и booking guard остаются в отдельных прежних хранилищах.

~~~dotenv
MODE=coordinated
SERVER_URL=https://visa-server.tailnet-name.ts.net
NODE_TOKEN={nodeId}.{secret}

# /ws и vhost visa задаются общим контрактом.
~~~

Для Cloudflare профилей меняется SERVER_URL: временный https://random-name.trycloudflare.com или постоянный https://visa.example.com. NODE_TOKEN остаётся прежним.

Минимальные настройки публикации сервера:

~~~dotenv
EXPOSE_MODE=tailscale
PUBLIC_BASE_URL=https://visa-server.tailnet-name.ts.net
# Другие значения: cloudflare_quick и cloudflare_domain.
# Для named tunnel серверу отдельно передаются tunnel credentials.
~~~

Solo не требует SERVER_URL, NODE_TOKEN, NODE_MIN_DATE и сетевого подключения Coordinator; зависимости сетевого транспорта не должны мешать запуску solo.

На сервере задать consulateId/city, учётные записи портала, EXPOSE_MODE, PUBLIC_BASE_URL, credentials приложения и provisioning, пути SQLite/томов. Команда первого запуска создаёт администратора и пользовательские аккаунты; публичная регистрация отключена. Интервалы первой версии: обычные проверки 180, heartbeat 30, отсутствие 540, свежесть heartbeat 60, находки 180 секунд.

Секреты, SQLite, сессии и runtime данные исключаются из Git. Административные credentials не входят в конфиг пользователя.

Истечение присутствия сохраняет регистрацию; свежие находки готовой ноды могут быть доставлены остальным активным участникам даже до восстановления её собственного присутствия.

SQLite сохраняет входящую дедупликацию, находки и исходящие события вместе с изменениями состояния. Pending события сохраняют messageId и абсолютный срок при перезапуске; отправленные брокеру помечаются отдельно. Повторный или старый heartbeat не обновляет присутствие. Исходный sentAt также сохраняется отдельно от lastSeenAt, чтобы допуск часов в пять секунд не позволял откатить личный порог.

Локальные команды без брокера:

~~~sh
usvisa-coordinator init-db --consulate-id 95 --city Vancouver
usvisa-coordinator state
# Необязательный --database PATH указывается перед подкомандой.
~~~

База по умолчанию — USVISA_DATA_DIR/.coordinator/state.sqlite3. state показывает сохранённое состояние без запуска сервиса. Сетевой consumer, периодический вызов expire, publisher confirms и выдача RabbitMQ доступа подключены этапами ниже; init-db сам по себе не создаёт брокер и не запускает coordinated Node.

Проверка этапа: 138 unit тестов проходят, включая 35 новых проверок контракта, фаз, свежести heartbeat, адресной фильтрации, рестарта SQLite, дедупликации и отката состояния вместе с outbox при ошибке записи. Реальный визовый сайт, SMTP и RabbitMQ в этих тестах не используются.

## Проверка реализации

Для переноса использовать существующие unit тесты. Для распределённой логики добавить проверки:

| Сценарий | Ожидаемый результат |
| --- | --- |
| Две ноды без пауз | Каждая раз в 180 секунд, сдвиг 90 секунд |
| Смена назначения сразу после проверки | Слишком ранняя точка пропускается |
| Три периода отсутствия | Исключение из состава, очередь и учётка сохраняются |
| Старый heartbeat после простоя | Не восстанавливает присутствие и не откатывает minDate |
| Старое расписание после нового | Меньшая revision игнорируется |
| UUID ноды отстаёт | Следующий heartbeat вызывает персональный снимок |
| Разные minDate | Промежуточная дата доставляется подходящему получателю |
| Дата не подходит отправителю | Может быть отправлена другим участникам |
| Своя подтверждённая бронь | Исключена из находки |
| TEST_MODE | POST отсутствует, подготовленная дата остаётся находкой |
| Повтор входящего события | Нет повторной задачи или второго booking POST |
| Сбой между commit, publish и ACK | Состояние восстанавливается через outbox и дедупликацию |
| Истечение между этапами | Срок не продлевается, событие игнорируется |
| 429 или длительный вход | Ограничения действуют, heartbeat не блокируется |
| Coordinator недоступен при живом брокере | Продолжается сохранённая сетка |
| Отозванный токен | Соединения закрыты, повторный STOMP CONNECT отклоняется |
| Частичное создание ресурсов | Повтор дозавершает ту же операцию |
| Два процесса с одним токеном | Второе broker соединение отклоняется |
| Tailscale профиль | HTTPS и /ws доступны только разрешённым участникам tailnet |
| Quick Tunnel профиль | Портал и Node работают через один временный origin без браузерного входа скрипта |
| Новый Quick Tunnel | Старый URL не используется как discovery; новый конфиг подключает прежний токен |
| Named Tunnel профиль | Адрес сохраняется при рестарте cloudflared |
| Смена профиля | Пользователи, токены, очереди и состояние сохраняются |
| Неверный TLS сертификат или hostname | Клиент отклоняет подключение |
| Неавторизованный HTTP или STOMP клиент | Нет доступа к чужим данным или сообщениям |
| Перенос файлов | Прежний guard по-прежнему блокирует второй POST |

Тесты визового сайта используют подменённые HTTP ответы. Интеграционные тесты брокера используют локальный RabbitMQ. Реальная бронь и Gmail письма при этих проверках не отправляются. UI проверяется в браузере отдельно.

Существующая команда:

~~~sh
python -m unittest discover -s tests/unit -t . -v
~~~

Для новых наборов добавить отдельные команды проверки AMQP Coordinator, STOMP/WSS Node, портала и трёх профилей публикации.

## Границы первой версии

Приоритеты получателей, несколько групп, RabbitMQ кластер, публичная саморегистрация, отдельная JWT/OAuth инфраструктура, обязательный Cloudflare Access, WARP, автоматический поиск нового временного URL, автоматический переход в solo, горячая смена режима и разрешение каждой проверки через сервер не входят в первую версию.

Будущий переход приватного профиля на Headscale касается сетевой настройки устройств, адреса и сертификата HTTPS/WSS. Контракт JSON и логика Node/Coordinator остаются прежними.
